SDD 開發流程與四道驗證閘

本圖把 docs/sdd-workflow.md 的巨觀主流程與微觀交付迴圈畫成一張圖，重點放在四件最容易被誤解的事： 四道驗證閘門互不取代、Red／Green 的角色分工、archive 只發生在 final PR group、 以及 Lightweight Path 的四個成立條件。政策正本仍是 docs/sdd-workflow.md，本圖只是它的視覺化摘要。

圖一 · 巨觀主流程與四道驗證閘

每個階段都是硬閘門。右欄四道驗證閘門各自只對其責任範圍負責，不能以單一「verify」名稱掩蓋差異；左側虛線是 Lightweight Path 旁路，四條件全數成立時才可走。

圖二 · 微觀交付迴圈：TDD 角色分工與交付時機

/opsx:apply 內部的一輪交付。三個角色的責任不重疊：senior-qa 先提交 Red、實作 agent 交付 Green、主 agent 驗證兩份證據且是唯一可更新 tasks.md checkbox 的角色。最下方兩格說明中間群組與最終群組的交付差異。

四道閘門的唯一責任

  • 閘門 1 OpenSpec schema validation — 只驗 schema、delta 與 scenario 結構。採 non-strict schema gate（openspec validate --changes --no-interactive），不驗專案 headings、ownership、status 與 retired path。
  • 閘門 2 Project SDD lint — 專案 headings 與 goal／status／ownership／retired-path 規則。工具落地前依 workflow checklist 與 review evidence 執行。
  • 閘門 3 Code/test gates — 受影響實作的 Red/Green evidence 與適用的 type、lint、unit、integration、prototype、E2E、security 指令，外加每個 PR 群組的審查證據。
  • 閘門 4 Source-Verify + write-back/archive — archive-time 正典 ID、version 與 Changelog 完整性，以及 archive 後逐條 grep 驗證 derived view 的每一條正典引用。
  • /opsx:verify 可跑適用檢查，但不取代任何一道閘門；openspec validate 也只是閘門 1。

Lightweight Path 的四個條件

  • ≤ 2 個生產程式檔變更（spec 與測試檔不計）
  • 不涉及 API 契約變更
  • 只需小幅度的 spec 行為更新
  • 不新增也不移除任何 FR／AC，只做釐清
  • 四條件全部成立才可走 TDD → 實作 → spec 一致性檢查 → /pr-flow；任一條件不確定就回到完整 OpenSpec change 流程。

三層 Sprint 對應

  • Planner ≈ /speckit.specify、/speckit.clarify 與 OpenSpec propose
  • Generator ≈ OpenSpec apply
  • Evaluator ≈ 驗證指令與 write-back Source-Verify gate
  • Generator 啟動後範圍即鎖定，sprint 中途不得追加項目。
